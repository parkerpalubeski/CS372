# CS 372 - Exploration 4: TCP and UDP

## Name a few protocols that rely on TCP for data integrity.

* HTTP
* HTTPS
* FTP
* SSH
* SMTP

## Why is there a three-way handshake to set up a connection? Why not just start transmitting?

This is to ensure that both sides are fully set up to transmit/receive as necessary. 

## How does a checksum protect against data corruption?

It's essentially a way to verify that all the data has been received intact. The sender computes the checksum based on the data, then transmits it along with the packet to the receiver. The receiver, without looking at the checksum, calculates the checksum itself, and compares it to what was sent by the sender. 

## What’s the main difference in the goals of Flow Control and Congestion Control?

Flow control is essentially a check on the throughput limit for the sender and receiver themselves. Congestion control is more concerned with the various nodes between them that the data must go through on the internet.

## Reflect on the reasons for switching between Slow Start and Congestion Avoidance. What advantages does each have in different phases of congestion detection?

Slow start's primary purpose is to test the network for its capacity. This allows it to find the expected throughput levels very quickly. Congestion avoidance seems more to find a maximum *stable* capacity, where packet loss is minimized but throughput is still high. 

## What is the purpose of Flow Control?

Flow control is to ensure the receiver isn't completely overwhelmed. Essentially, ensuring that even if the network can handle higher throughputs, the receiving device itself is only receiving data it can actually handle.

## What does TCP provide that UDP does not in terms of delivery guarantees?

TCP offers validation for packets, ensuring that all data arrives, complete and uncorrupted. This includes checksums, ACKs, and verifying throughput capacity.

## Why do people recommend keeping UDP packets small?

There are maximum packet sizes called MTUs that must be observed. A larger packet might be limited to higher MTU routes from source to destination, or may not be able to reach it at all. 

Additionally, if a fragment is lost, the entire packet is discarded. With an exceptionally large packet, this could be devastating. 

## Why is the UDP header so much smaller than the TCP header?

UDP doesn't have any of the "three-way handshake" data that a TCP header has, so as a consequence, UDP headers are much smaller. There is no verification of data integrity, or packet reassembly.

## sendto() requires you specify a destination IP and port. Why does the TCP-oriented send() function not require those arguments?

When send is called, TCP has already established the connection via connect()/accept(), so the IP address and port are already known.

## Why would people use UDP over TCP if it’s relatively unreliable?

Whenever a connection requires consistent uptime, UDP is a better choice. This is usually for when there is a constant stream of data, and immediacy is essential. 

For video as an example, TCP *might* be used for a youtube video, but for a livestream for instance, UDP would *absolutely* be the better choice to ensure that the video feed doesn't become more consistently delayed as packets are lossed and reacquired. 

Another example is video games. TCP would be best suited for turn-based games like Chess where a slight delay in receiving packets is acceptable, but for a First-Person-Shooter like Call of Duty, UDP would absolutely be a better choice since a split second can make all the difference in gameplay.

UDP simply trades the reliability and completeness of the received data for lower latency. I like to think of it as kind of a "greedy" way of receiving data.
